## Deploy Workflow
1. Kill any running dev server before `rm -rf .next` (deleting it while `dev` is running corrupts the build).
2. `rm -rf .next && npx --yes pnpm@latest build` — read both the head (compiled successfully / TS errors) and tail (route list) of the output.
3. If you need a local visual check first, flip `PREVIEW_BYPASS = true` in `src/app/(app)/layout.tsx` (bypasses the Firebase auth redirect), test, then **always revert it** before the next build — never let it reach a deploy.
4. `npx --yes vercel --prod --yes --scope subs-3909s-projects` to deploy, then check the response for `"target": "production"` and the aliased URL. Omit `--prod` for a non-production preview link (those sit behind Vercel SSO by default — team login required to view).
5. Before `git add`: run `git status --porcelain` and confirm only the intended files changed — no `.next/`, `node_modules/`, or `.env*`. This is a standing rule, not optional.
6. `git fetch origin && git log HEAD..origin/main --oneline` before pushing, in case someone else pushed in the meantime.
7. **If there's an unconfirmed/unreviewed change sitting in the working tree** (e.g. the user hasn't said "yes, ship it" yet) while you're deploying something else that IS confirmed: `git stash push -- <file> <file>` those specific files first, deploy+push the confirmed work, then `git stash pop` to restore them. Never let an unconfirmed change ride along in a deploy just because it happened to be sitting in the same working tree.

## Known Gotchas (read before touching these again)

- **HubSpot Search API caps at 18 filters total across all filterGroups in one request.** If you need another OR-branch (e.g. widening `lead_form_type` matching), it will silently 500 once you cross that limit. Fix: split into a **separate parallel search request** instead of adding a 5th filterGroup — see `searchAll` calls in `src/app/api/hubspot/mqls/route.ts` for the pattern.
- **claude.ai `/public/artifacts/*` links can never be embedded in an iframe, anywhere, ever.** This is a domain-wide `frame-ancestors 'self'` CSP header, not specific to any one artifact URL — a *new* artifact link will hit the exact same wall. If someone wants a claude.ai artifact embedded on this dashboard, the actual fix is standing up the component as its own small Next.js app and deploying it to its own Vercel project (see `events-performance-dashboard` — a sibling directory to this one — for the pattern), then iframing *that* URL.
- **Never round-trip a parsed sheet/date string through `.toISOString()` for date-only comparisons.** `new Date("Aug 5, 2026")` parses in the *server's local timezone*; this dev environment runs in IST (UTC+5:30) while Vercel's production functions run in UTC, so the same code silently shifts dates by a day depending on where it runs. Fix: extract `getFullYear()/getMonth()/getDate()` (local components — correct since the source string had no time-of-day/timezone info to begin with) into a plain `YYYY-MM-DD` string, and compare dates as strings, not `Date` objects. See `parseSheetDate` in `src/app/api/sdr-sql-tracker/route.ts` or `src/app/api/sdr-activity/route.ts`.
- **The SDR tracker spreadsheet (`1REVpGqF-E_0WNQgUJ1xNA41MCO-zOFfWJ1Q7dznsCG4`) has multiple tabs — don't assume the first/obvious one is live data.** `SDR Weekly Activity` is hidden and stopped being updated around mid-2026 (only ~3 SQLs total, ever) — `src/app/api/sdr-activity/route.ts` reads this one, feeding the Sales Performance page. `Meetings Booked` is the tab SDRs actually keep current (7000+ row capacity, real weekly entries through the present) — one row per lead, with `SQLs` / `Qualified Opportunity` / `Closed Won` / `Closed Lost` as Yes/No columns and an `Expressed Interest Date` to bucket by week. `src/app/api/sdr-sql-tracker/route.ts` reads this one — as of 2026-09-07 it no longer feeds any chart on the MQL page (see next bullet), but keep the route since other things may still call it; before trusting any tab in a multi-tab sheet, check `sheets.properties` via the Sheets API for `hidden: true` and look at how recent the actual data rows are — don't just trust the tab name.
- **`/api/hubspot/pipeline-trend` (Pipeline Generated Trend chart + Pipeline Metrics cards on the MQL page) is scoped to "marketing efforts driven" deals only, as of 2026-09-07** — same `deal_source in {Direct, Inbound, Marketing}` + `contact_lead_form_type contains Book a Demo` filter as `/api/hubspot/sql-to-opportunity-monthly` (see that entry below for the full rationale). Previously this route pulled every deal in the Studio Deals pipeline regardless of source, so the chart included HyperScalers/SI Partner/Referral/Partner Lead/Event-sourced pipeline too — the user flagged this as overstating marketing's contribution. Unlike the SQL→Opportunity chart, this one stayed **weekly** (8-week trend) per explicit request — don't change its granularity without asking.
- **The MQL page's Qualification Funnel was split into two independent, single-dimension tables on 2026-09-07 — `MQLLeadStatusFunnel` and `MQLLifecycleStatusFunnel` (both in `src/components/mql/MQLScoreCards.tsx`), replacing the old single `QualificationFunnel`.** Root cause: the old merged funnel checked `lifecyclestage` FIRST (via `SQL_STAGES_CUMULATIVE`) before falling back to `hs_lead_status` when bucketing a contact, so a contact who'd already progressed to SQL but still had a stale `hs_lead_status` of "Demo Completed" (real example: Schalk Heunis, Vodacom) silently vanished from the Demo Completed row and only showed up under SQL — while HubSpot's own contact record, and this dashboard's own Priority Details table (which prints raw `hs_lead_status`), plainly showed "Demo Completed". The fix: `/api/hubspot/mqls/route.ts` now computes two fully independent bucket sets per contact — `lead_status_breakdown`/`lead_status_stage_breakdown` (pure `hs_lead_status`, never consults `lifecyclestage`) and `lifecycle_status_breakdown`/`lifecycle_status_stage_breakdown` (pure `lifecyclestage`, current-stage-exact via `SQL_EXACT`/`OPP_EXACT`, never consults `hs_lead_status`) — each sums cleanly to the total MQL count on its own. The old merged `mql_status_breakdown`/`stage_breakdown` fields are UNCHANGED and still returned (still used elsewhere) — don't delete them. The old "MQL Journey" section (`MQLJourneyFunnel.tsx`) was renamed **"Consolidated MQL Lifecycle Status"** and narrowed to drop its Demo Booked/Demo Completed rows (now fully covered by the new Lead Status funnel) — it's pure lifecyclestage progression now: Total MQLs → SQL → Opportunity → Customer.
  - **Gotcha hit while building this**: adding new fields to `/api/hubspot/mqls`'s JSON response is NOT enough on its own — `src/components/mql/MQLHubSpotData.tsx`'s `onData` callback prop only forwards a fixed allowlist of fields up to the parent page (`mqls/page.tsx`), so a new backend field silently never reaches `enrichedData` unless it's ALSO added to `onData`'s type signature AND the actual `onData?.({...})` call inside `fetchData()`. This caused the funnel tables to render all-zero even though the raw API response (verified via curl and via the browser's own Network tab) had the correct numbers the whole time — the bug was in this one missed forwarding step, not caching, not dev-server staleness. If a new `/api/hubspot/mqls` field ever needs to reach the MQL page's UI again, check this file first.
- **The MQL page's two SQL-related trend charts now use two different HubSpot-based approaches, not the SDR tracker sheet — both flipped away from the sheet on 2026-09-07.** `MQLToSQLConversionChart.tsx` (MQL → SQL %) stayed **weekly**, sourcing SQL from `funnel.sql` off `/api/hubspot/mqls` (contact-based, current-lifecyclestage-exact). `SQLToOppConversionChart.tsx` (SQL → Opportunity %) was changed from weekly to **monthly** (last 4 months, trailing off the real current month) and now hits its own dedicated route, `/api/hubspot/sql-to-opportunity-monthly` — reason: a contact moving all the way from SQL to Opportunity inside one calendar week is rare, so the weekly version read flat 0% almost every week and wasn't useful on a call. - **The MQL page's "MQL Journey" funnel (`MQLJourneyFunnel.tsx`, fed by `monthToDateFunnel` in `src/app/(app)/mqls/page.tsx`) is anchored to the REAL current calendar month (today's date, 1st through yesterday) — deliberately independent of the page's week/date-range picker.** It previously derived the month from the *selected week's* start date but still extended the end out to the picker's `queryEnd`; whenever the selected week straddled a month boundary (e.g. the default "previous completed week" starting Aug 31 and running through Sep 6), that silently produced a cross-month range (Aug 1 – Sep 6, inflating "Total MQLs" to 315+) instead of one calendar month. - **"Open Pipeline (This Quarter)" and "Q3 Progress" on the Opportunity ACV Pipeline card are deliberately two different numbers, computed two different ways** — conflating them into one calculation is an easy, already-made-once mistake:
  - *Open Pipeline (This Quarter)*: any still-open deal (any create date) with a **closedate** in Q3. The broad "what's left to land by Sep 30" view.
  - *Q3 Progress*: only deals **created** in Q3 that are **also** closing in Q3 (same-quarter velocity) — a narrower, historically-established metric. Always compute these from two independent loops over the full deal set; don't let one derive from the other's intermediate data structure.
- **Enriching HubSpot deal company/source (`fetchDealCompany`/`fetchDealSource` in `deals-acv/route.ts`) does 2 sequential API calls per deal.** Fine for a single quarter (~200 deals) but will time out a serverless function against the full unfiltered pipeline (900+ deals). Keep this capped (currently top 150 by amount) rather than removing the cap.

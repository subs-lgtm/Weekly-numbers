## Deploy Workflow
1. Kill any running dev server before `rm -rf .next` (deleting it while `dev` is running corrupts the build).
2. `rm -rf .next && npx --yes pnpm@latest build` — read both the head (compiled successfully / TS errors) and tail (route list) of the output.
3. If you need a local visual check first, flip `PREVIEW_BYPASS = true` in `src/app/(app)/layout.tsx` (bypasses the Firebase auth redirect), test, then **always revert it** before the next build — never let it reach a deploy.
4. `npx --yes vercel --prod --yes --scope subs-3909s-projects` to deploy, then check the response for `"target": "production"` and the aliased URL. Omit `--prod` for a non-production preview link (those sit behind Vercel SSO by default — team login required to view).
5. Before `git add`: run `git status --porcelain` and confirm only the intended files changed — no `.next/`, `node_modules/`, or `.env*`. This is a standing rule, not optional.
6. `git fetch origin && git log HEAD..origin/main --oneline` before pushing, in case someone else pushed in the meantime.
7. **If there's an unconfirmed/unreviewed change sitting in the working tree** (e.g. the user hasn't said "yes, ship it" yet) while you're deploying something else that IS confirmed: `git stash push -- <file> <file>` those specific files first, deploy+push the confirmed work, then `git stash pop` to restore them. Never let an unconfirmed change ride along in a deploy just because it happened to be sitting in the same working tree.

## Known Gotchas (read before touching these again)

- **HubSpot Search API caps at 18 filters total across all filterGroups in one request.** If you need another OR-branch (e.g. widening `lead_form_type` matching), it will silently 500 once you cross that limit. Fix: split into a **separate parallel search request** instead of adding a 5th filterGroup — see `searchAll` calls in `src/app/api/hubspot/mqls/route.ts` for the pattern.
- **claude.ai `/public/artifacts/*` links can never be embedded in an iframe, anywhere, ever.** This is a domain-wide `frame-ancestors 'self'` CSP header, not specific to any one artifact URL — a *new* artifact link will hit the exact same wall. If someone wants a claude.ai artifact embedded on this dashboard, the actual fix is standing up the component as its own small Next.js app and deploying it to its own Vercel project (see `events-performance-dashboard` — a sibling directory to this one — for the pattern), then iframing *that* URL.
- **Never round-trip a parsed sheet/date string through `.toISOString()` for date-only comparisons.** `new Date("Aug 5, 2026")` parses in the *server's local timezone*; this dev environment runs in IST (UTC+5:30) while Vercel's production functions run in UTC, so the same code silently shifts dates by a day depending on where it runs. Fix: extract `getFullYear()/getMonth()/getDate()` (local components — correct since the source string had no time-of-day/timezone info to begin with) into a plain `YYYY-MM-DD` string, and compare dates as strings, not `Date` objects. See `parseSheetDate` in `src/app/api/sdr-sql-tracker/route.ts` or `src/app/api/sdr-activity/route.ts`.
- **The SDR tracker spreadsheet (`1REVpGqF-E_0WNQgUJ1xNA41MCO-zOFfWJ1Q7dznsCG4`) has multiple tabs — don't assume the first/obvious one is live data.** `SDR Weekly Activity` is hidden and stopped being updated around mid-2026 (only ~3 SQLs total, ever) — `src/app/api/sdr-activity/route.ts` reads this one, feeding the Sales Performance page. `Meetings Booked` is the tab SDRs actually keep current (7000+ row capacity, real weekly entries through the present) — one row per lead, with `SQLs` / `Qualified Opportunity` / `Closed Won` / `Closed Lost` as Yes/No columns and an `Expressed Interest Date` to bucket by week. `src/app/api/sdr-sql-tracker/route.ts` reads this one, feeding the MQL page's WoW conversion charts. Before trusting any tab in a multi-tab sheet, check `sheets.properties` via the Sheets API for `hidden: true` and look at how recent the actual data rows are — don't just trust the tab name.
- **MQL definition is strictly `lead_form_type = Book a Demo`.** Contacts entered directly by SDRs/ops (offline imports with no `lead_form_type`) are deliberately excluded from every MQL/SQL/Opportunity count derived from `/api/hubspot/mqls` — they didn't come through a marketing form, so by this dashboard's definition they aren't MQLs, no matter how well-qualified. Don't re-add an ID-based merge/backfill for "known good" contacts outside this definition — it was tried, reverted, and explicitly rejected.
- **"Open Pipeline (This Quarter)" and "Q3 Progress" on the Opportunity ACV Pipeline card are deliberately two different numbers, computed two different ways** — conflating them into one calculation is an easy, already-made-once mistake:
  - *Open Pipeline (This Quarter)*: any still-open deal (any create date) with a **closedate** in Q3. The broad "what's left to land by Sep 30" view.
  - *Q3 Progress*: only deals **created** in Q3 that are **also** closing in Q3 (same-quarter velocity) — a narrower, historically-established metric. Always compute these from two independent loops over the full deal set; don't let one derive from the other's intermediate data structure.
- **Enriching HubSpot deal company/source (`fetchDealCompany`/`fetchDealSource` in `deals-acv/route.ts`) does 2 sequential API calls per deal.** Fine for a single quarter (~200 deals) but will time out a serverless function against the full unfiltered pipeline (900+ deals). Keep this capped (currently top 150 by amount) rather than removing the cap.
- **This portal's `lifecyclestage` internal values do NOT match their display labels — always verify with `get_properties` before trusting a value name.** Confirmed directly against the property definition: `opportunity` (internal) is labeled **"SQL (Sales Qualified Lead)"**, `249550600` is labeled **"Opportunity"**, and `242934529` is labeled **"Discarded"** (not a funnel stage at all — don't include it in any MQL+/SQL+ set). A value literally named `salesqualifiedlead` is not even a valid option in this portal (any filter using it silently matches zero contacts). `src/app/api/hubspot/mqls/route.ts` has `SQL_EXACT`/`OPP_EXACT` (current-stage-only, matches HubSpot's own UI filter exactly) and `SQL_STAGES_CUMULATIVE`/`OPP_STAGES_CUMULATIVE` (reached-this-stage-or-further) as two clearly-separated sets for a reason — the dashboard's SQL/Opportunity scorecards use the exact-only ones (confirmed against a direct user comparison: HubSpot UI showed 57, cumulative gave 75, both were "correct" for different questions — user chose exact-only), while the `lifecycle_stage_funnel` leakage breakdown and the qualification-funnel table's bucket assignment intentionally keep the cumulative ones. Don't collapse these back into one set.
- Standing rule (already in memory, repeating here since it's load-bearing): **never push `.next/`, `node_modules/`, or `.env*` files** — verify `.gitignore` and `git status --porcelain` before every commit, not just the first one.
- **`/api/working-leads-sync` (`src/app/api/working-leads-sync/route.ts`) is a manual-trigger-only route** — pulls "Working MQLs" (createdate in June/July/August 2026, Book a Demo, current lifecyclestage exactly `marketingqualifiedlead` — same definition as the Predictive Funnel) into the "Working lead status" Google Sheet (`1WuUzeCGRFsy44bH_OEerBzFkifJoR0Lw8ZHGRg0v4lM`, tab `Sheet1`), for the sales team's call-prep list. Trigger it with `curl http://localhost:3000/api/working-leads-sync` while the dev server is running, or ask Claude to "refresh the working leads sheet." It's a full clear-and-rewrite every run (no diffing), so it always exactly reflects HubSpot's current state — a lead that's progressed past MQL or been discarded simply won't appear next run. **Deliberately NOT automated on a schedule** — the user considered hourly cloud-scheduled automation but declined once it became clear that requires deploying this app (violates the standing "local preview only" instruction) and exposing HubSpot/Google credentials to a cloud environment; chose manual-trigger-only instead. Don't add scheduled automation for this route without re-confirming that tradeoff explicitly. `inbound_owner` and `hubspot_owner_id` are both HubSpot **owner IDs** (not names) — both must be resolved through the same `/crm/v3/owners` map; a naive first pass at this route printed `inbound_owner`'s raw numeric ID before that fix.
- **A contact's `lifecyclestage = 'customer'` does NOT reliably mean there's a real Closed Won deal behind it — verify against the Deal record before trusting it.** Confirmed directly on two real contacts: Jeff Asiedu (lifecyclestage=customer) has one associated deal, and it's in the **"Dropped"** stage; Jose Diaz (lifecyclestage=customer) has two associated deals, both still in early open stages ("Discovery Call", "Solution Validation") — neither anywhere near closed. The Executive Dashboard's "Customers Won" (`src/app/api/hubspot/executive-cohorts/route.ts`, `classifyOutcomes()`) deliberately does NOT trust the Contact's `lifecyclestage` label at all — it checks every contact's actual associated Deal(s) in the Studio Deals pipeline for `dealstage === '982194449'` (Closed Won), per explicit user instruction ("take it from the opportunity section"). This means Customers Won numbers can look surprisingly low compared to a naive `lifecyclestage='customer'` count — that's the deal-verified number correctly exposing a Contact/Deal data-quality gap, not a bug. User explicitly confirmed to keep this strict (deal-verified only, no lifecyclestage fallback) rather than loosening it — don't add an OR-with-lifecyclestage fallback without asking first.
- **A contact's `createdate` (Book a Demo form submitted) and its `hs_v2_date_entered_marketingqualifiedlead` (HubSpot's automation actually marking it MQL) can be weeks-to-months apart, or the second one can never happen at all.** Confirmed directly: of 12 Book-a-Demo contacts created in March 2026, zero were marked MQL by HubSpot's lifecycle automation *during March* — several crossed into MQL stage in May/June instead, a few are still stuck at "lead" and may never get marked, and a couple skipped MQL entirely and went straight to SQL the same day they were created. This means the Executive Dashboard's event-dated "MQLs Created" (`src/app/api/hubspot/executive-flow/route.ts` and `executive-cohorts/route.ts`, both filtering on `hs_v2_date_entered_marketingqualifiedlead`) will show much lower, laggier numbers than the original MQL dashboard's count (`src/app/api/hubspot/mqls/route.ts`, which counts by `createdate` and doesn't require the contact to have ever reached MQL lifecycle stage at all) — **this is not a bug, the two are deliberately answering different questions** (form submitted vs. actually qualified by HubSpot's workflow). Confirmed with the user, who chose to keep the strict event-date definition on the Executive Dashboard rather than falling back to `createdate` — don't "fix" this divergence by making them match.
